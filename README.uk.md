## Проблема

За довгу сесію накопичується вистраждане розуміння того, чому код саме такий. Далі контекст стискається — і це зникає. У наступній сесії агент перечитує ті самі файли, повторно виводить ті самі висновки й виставляє вам рахунок за ті самі токени.

`CLAUDE.md` не масштабується далі кількох десятків рядків і не вміє відповісти на питання *«що ми вирішили щодо X і чому?»*.

**Turbo Quant Memory** — це MCP-сервер, який дає агенту постійне сховище з пошуком, куди той пише під час роботи: рішення, уроки, патерни, передання між сесіями, а також компактний індекс вашого Markdown. Пошук повертає картки результатів приблизно на 220 символів замість цілих документів; повний вміст агент довантажує лише тоді, коли картки не вистачає.

## Чому саме цей

|                              | **Turbo Quant Memory**                     | mem0 / OpenMemory          | MCP-сервер `memory` |
| :--------------------------- | :----------------------------------------- | :------------------------- | :------------------ |
| Де лежать дані               | завжди на вашому диску                      | хмара вендора або самохост | на вашому диску     |
| Дані покидають машину        | **ніколи**                                  | так, якщо не самохост      | ніколи              |
| Пошук                        | гібридний BM25 + вектор, злиття через RRF   | щільний вектор             | точний обхід графа  |
| Що повертає запит            | компактні картки, довантаження за потреби   | повні спогади              | повні вузли         |
| Граф знань                   | так — з життєвим циклом і лінтингом          | ні                         | так                 |
| Неанглійський вміст          | кирилиця збігається точно «з коробки»        | по-різному                 | —                   |
| Рахує власну економію        | **так — `server_info()`**                   | ні                         | ні                  |
| Ціна                         | безкоштовно, MIT                            | платні тарифи              | безкоштовно         |

Жодного HTTP-клієнта, жодної телеметрії, жодних «дзвінків додому». Перевірте самі — команда нічого не поверне:

```bash
grep -rnE '^[[:space:]]*(import|from)[[:space:]]+(requests|httpx|aiohttp|urllib3)\b' src/
```

Точності заради, один виняток: при першому запуску `fastembed` завантажує модель ембедингів (~0,22 ГБ) з Hugging Face. Після цього сервер працює повністю офлайн. Ваші нотатки, код і секрети не передаються нікуди — у пакеті просто немає коду, здатного їх надіслати.

## Встановлення

### Доручіть встановлення агенту

Вставте це в Claude Code, Codex, Gemini CLI, Cursor або Antigravity:

> Встанови та налаштуй MCP-сервер Turbo Quant Memory для цього робочого простору з
> https://github.com/Lexus2016/turbo_quant_memory — дій за README, зареєструй сервер
> `tqmemory`, виконай `turbo-memory-mcp skill install`, проведи перевірку працездатності
> та проіндексуй цей проєкт.

`skill install` копіює інструкцію з експлуатації в усі каталоги навичок агентів на машині, тож кожна наступна сесія вже знає, як користуватися пам'яттю, без окремих пояснень.

### Або встановіть вручну

```bash
uv tool install turbo-quant-memory
```

Далі зареєструйте сервер у своєму клієнті:

```bash
claude mcp add --scope project tqmemory -- turbo-memory-mcp serve   # Claude Code
codex  mcp add tqmemory -- turbo-memory-mcp serve                   # Codex
gemini mcp add tqmemory turbo-memory-mcp serve                      # Gemini CLI
```

Cursor, OpenCode, Antigravity та інші клієнти → [CLIENT_INTEGRATIONS.uk.md](CLIENT_INTEGRATIONS.uk.md).
Hermes запускає MCP через systemd-шлюз → [docs/hermes.uk.md](docs/hermes.uk.md).

## Що він робить

* **Типізовані нотатки.** `decision`, `lesson`, `pattern`, `handoff` — кожна зберігається з тегами, походженням і зв'язком у графі знань до файлу чи задачі, якої стосується.
* **Рівні пам'яті.** `durable` (рішення, патерни) і `reference` (проіндексовані документи) шукаються за замовчуванням; `episodic` (передання між сесіями) не заважає, доки ви його не попросите, тож учорашній шум ніколи не ховає архітектурне рішення.
* **Гібридний пошук.** Веде щільний векторний канал; канал BM25 рятує точні терміни — імена функцій, шляхи до файлів, ідентифікатори — і зливається через Reciprocal Rank Fusion. Кирилиця та інші неанглійські терміни збігаються точно, без урахування регістру й діакритики, без жодних налаштувань.
* **Граф знань.** Спрямовані зв'язки з мітками часу між нотатками, файлами та задачами. Результати пошуку несуть пов'язаний контекст усередині, тож агенту не потрібен другий запит.
* **Нотатки людини важать більше за нотатки агента.** Усе, що ви явно попросили запам'ятати, позначається як `human-explicit` і за однакової релевантності стоїть вище власних спостережень агента.
* **Зашифроване сховище секретів.** Прив'язане до проєкту, AES-256-GCM, структурно недосяжне для пошуку. → [docs/secrets-vault.uk.md](docs/secrets-vault.uk.md)
* **Працює на слабкій машині.** Ембедер за замовчуванням — ONNX через fastembed: без PyTorch, модель ~0,22 ГБ, комфортно на 2 ГБ оперативної пам'яті.
* **Кілька агентів в одному проєкті — автоматично.** Агенти, що працюють в одному git-робочому дереві, бачать сесії один одного, заявлену роботу та нещодавні зміни файлів; поки їх двоє або більше, зміни текстових файлів записуються, щоб їх можна було відновити. Налаштування не потрібне.

Повні технічні подробиці → [docs/features.uk.md](docs/features.uk.md)

## Кілька агентів в одному проєкті

Якщо ви запускаєте кількох агентів в одному робочому дереві, tqmemory пов'язує їх автоматично. Нічого налаштовувати не потрібно.

* **Агенти бачать один одного.** `workspace_status` показує активні сесії й оголошені ними завдання (`announce_work`, `finish_work`) та файли, що нещодавно змінювалися. Сесія, яка 30 хвилин не викликала tqmemory, потрапляє до `idle_sessions`: вона не вважається активною, а її оголошені області не входять до `overlaps`. Інші відповіді tqmemory містять коротку позначку `workspace` лише тоді, коли сталося щось нове, і ніколи — для єдиної сесії. Відповіді `health` і `server_info` завжди містять блок діагностики робочого простору.
* **Зміни записуються.** Поки дві або більше сесій працюють в одному git-робочому дереві, записуються нові версії текстових файлів, які змінюються (до 1 MiB на файл; файли, що відповідають `.gitignore` або `.tqmemoryignore`, пропускаються). Кілька швидких записів підряд можуть злитися в одну версію. `file_history` показує версії, `restore_file` повертає потрібну; саме відновлення теж можна скасувати. Те саме доступно з термінала: `turbo-memory-mcp files log` і `turbo-memory-mcp files restore`.
* **Ліміти.** Версії записуються лише тоді, коли дві або більше сесій працюють в одному git-робочому дереві. Журнал ніколи не працює поза git, у домашній теці чи в корені файлової системи. Типові значення: 1 MiB на файл, 256 MiB на проєкт як орієнтовний ліміт розміру і 14 днів зберігання. Записані версії лишаються доступними для відновлення 14 днів; старші, а також найстаріші версії понад ліміт розміру видаляються. Найновіша версія кожного файлу, зміненого за останні 24 години, за розміром не видаляється. Ці значення задають `TQMEMORY_JOURNAL_MAX_FILE_BYTES`, `TQMEMORY_JOURNAL_MAX_BYTES` і `TQMEMORY_JOURNAL_RETENTION_DAYS`; ліміт розміру є орієнтиром, а не жорстким максимумом.

Це частковий захист, який не гарантує збереження всіх змін. Запис не блокується, тож два агенти все ще можуть перезаписати роботу один одного; tqmemory лише показує це й допомагає відновити. Агенти, які ніколи не викликають tqmemory, нічого не бачать. Працює лише на одному комп'ютері. Щоб вимкнути, встановіть `TQMEMORY_WORKSPACE_DISABLE=1`.

## Пам’ять одного проєкту в іншій папці

Для тимчасового вибору без прив’язки папки викличте `list_projects()`, а потім `select_project(project_id="<ідентифікатор>")`. Поточне підключення MCP одразу користується пам’яттю цього проєкту. `select_project()` повертає автоматичне визначення. Вибір не змінює початкову папку проєкту й не індексує місцеві файли. Явне `TQMEMORY_PROJECT_ID` не повинно суперечити вибраному ідентифікатору.

`list_projects()` показує збережені проєкти: сталі ідентифікатори, назви, мітки, початкові папки й додаткові прив’язки. У терміналі цей перелік показує `turbo-memory-mcp projects`. Щоб користуватися пам’яттю наявного проєкту з нової папки, агент викликає `bind_project(project_id="<ідентифікатор>", path="/абсолютний/шлях/до/папки")`. Прив’язка зберігається локально й одразу діє для поточного підключення агента. `server_info()` підтверджує вибраний проєкт. `set_project_labels(project_id, labels=[...])` змінює мітки для відображення; мітки не визначають проєкт. `unbind_project(path="/абсолютний/шлях/до/папки")` прибирає точну прив’язку.

Прив’язувати можна лише наявний ідентифікатор. Сама прив’язка не індексує файли нової папки: для цього окремо викликають `index_paths`. Прив’язка стосується точної папки, тому вкладений репозиторій не підхоплюється мовчки. Якщо папку замінено або змінено її зареєстровану адресу Git, програма вимагатиме нової явної прив’язки. Налаштування `TQMEMORY_PROJECT_ID`, якщо воно задане, має вищий пріоритет.

Інструменти пам’яті працюють із вибраною папкою; `workspace_status`, `file_history` і `restore_file` надалі стосуються початкового робочого дерева процесу MCP.

Після перенесення знімка сховища на інший комп’ютер записи проєктів, глобальні записи, мітки та зашифровані секрети зберігаються. Прив’язки папок містять абсолютні шляхи старого комп’ютера: виберіть проєкт через `select_project` і за потреби прив’яжіть папки заново. Для читання секретів потрібен початковий пароль або ключ зі сховища ключів системи.

## Автоматичне обслуговування індексів

Головний процес MCP, який володіє сховищем, перевіряє пошукові індекси одразу після запуску та кожні шість годин роботи. Він обслуговує таблиці з непроіндексованими рядками повнотекстового пошуку або версіями старшими за сім днів. Робота йде у фоні під блокуванням запису проєкту в межах цього процесу; під час оптимізації запит до нього може тимчасово отримати відповідь «зайнято». Незалежні автономні процеси й команди термінала не охоплені цим блокуванням: конфлікт запису фіксується, а спроба повторюється під час наступної перевірки. Клієнти-посередники й автономні процеси не запускають обслуговування. Початкові файли Markdown і основні JSON-нотатки не змінюються. Команда `turbo-memory-mcp index-status` показує обсяг, вік версій і покриття повнотекстового індексу без зміни даних.

LanceDB зберігає недавні версії сім днів, тому на активній таблиці обслуговування може тимчасово збільшити обсяг. Не видаляйте файли LanceDB вручну. Якщо сховищем ще володіє старий процес MCP, перезапустіть його клієнти, щоб новий процес запустив обслуговування.

Перше повне узгодження старої таблиці один раз перебудує її вектори. Далі незмінені рядки пропускаються, доки збігаються модель, спосіб обчислення векторів і версія відповідної бібліотеки. Їхня зміна перебудує вектори під час наступного повного узгодження; регулярне обслуговування саме по собі цього не робить.
